## 3. 长期有效的决策逻辑

以下汇总当前实施方案的约束。其中工程目录与初始化已落地，其余能力仍需按任务表实现并验收。后续如调整，应追加决策并说明替代关系。

### DEC-01：交付公共上下文输入，先验证一条业务流程

公共能力负责整理、确认和发布稳定输入，供用例生成与接口自动化共同消费；接口执行器保留在原专项内，不在本项目重写所有脚本框架。

首期采用文件导入，范围为 PRD、接口文档、人工确认和已有业务规则，历史用例与脱敏日志作补充。全量同步、UI 自动执行、多业务扩展、多 Agent、语义检索、管理后台列入后续阶段。“作业辅导”仅为候选，具体流程和权限在 D1 核实。

依据：实施计划第 1、7 节。关联任务：P1-01～04、P3-01～05。状态：计划方案，业务范围待确认。

### DEC-02：先定义数据契约，再实现 Agent

以六类核心对象统一生成、存储和消费；使用 Pydantic 校验并导出 JSON Schema。规则与来源引用固定修订，`schema_version`、`package_revision`、`target_scope` 分别表示格式、包版本和业务适用范围，不能混用。

先明确字段和约束，再接入模型分析，降低不同模块对“规则”“版本”“已确认”的解释差异。当前 `schemas/` 仅有说明，不能视为契约冻结。

依据：实施计划第 4 节、`schemas/README.md`。关联任务：P1-06、P3-01。状态：计划方案，尚未实现。

### DEC-03：Agent 生成草稿，应用控制状态、确认和发布

首期一个主 Agent 负责检索、抽取、比对、映射和问题草稿。固定状态机由应用执行，正式事实确认和发布通过受控入口完成；`approve_changes`、`publish_package` 不作为 Agent 可任意调用的工具。

确认人、时间和依据必须来自实际确认记录，不能因模型填入姓名或 `confirmed` 就生效。来源文档与日志是分析材料，不得改变工具权限和发布流程。校验失败回草稿，运行失败记录阶段及恢复点。

依据：实施计划第 3.3、5 节、`docs/architecture.md`。关联任务：P1-10～12、P2-02～06。状态：计划方案，状态机和确认/发布尚未实现。

### DEC-04：证据、草稿、确认事实和发布包分开管理

来源更新产生新快照，草稿允许修改，确认事实生成新修订且保留历史，已发布包不可覆盖。`expected`、`observed`、`inferred` 分别表示预期、观察和推断；运行观察不能自动升级为业务验收预期。

每条规则应有可定位依据；引用存在只证明可找到证据，语义是否支持结论仍需人工评审或独立评测。接口未知时保留问题，不编造接口名。

依据：实施计划第 3.3、4、5.1 节。关联任务：P1-06、08、12、P2-01、04、07。状态：数据目录已落地，业务语义及修订控制待实现。

### DEC-05：业务事实库与 Agent 运行状态独立

单机试点计划使用 SQLite 保存事实，文件目录保存原文和包；`facts.sqlite3` 与 `runs/checkpoints.sqlite3` 分开。前者用于跨需求查询事实修订，后者用于恢复分析任务；会话草稿和对话摘要不能充当长期事实库。

事实检索先采用业务标签、版本过滤和关键词，默认只返回适用范围内的已确认事实；有漏检证据后再评估语义检索。多人服务化时再评估 PostgreSQL。当前仅预留数据库路径，初始化不创建数据库。

依据：实施计划第 3.2、5.2 节、`src/workflow/config.py`。关联任务：P1-09、11、P4-02、03。状态：路径已落地，数据库、检索和持久化恢复待实现。

### DEC-06：发布必须确定、不可变、可追溯且幂等

发布前程序校验格式、来源/修订可读性、真实确认、目标版本、场景完整性、取证方式和阻塞问题。仅发布部分范围时，记录排除场景及原因，并取得测试负责人对范围的确认，不能声称完整覆盖。

正式包包含六个约定文件，并冻结事实内容、来源、修订和配置。发布需具备事务及幂等控制，保证失败重试不产生同一版本的不同内容。两端以相同的包 ID、包修订和 manifest 哈希确定共同输入。

依据：实施计划第 4.3、5.5 节。关联任务：P2-04～08、P3-01、04、P4-03。状态：计划方案，发布服务尚未实现。

### DEC-07：反馈修正产生新版本，历史结果保持原引用

消费端提交包/场景 ID、错误类型、证据和修正建议，事实变更重新确认后产生新规则修订和新包。消费端显式选择切换；旧包和历史执行结果不被覆盖。

用例输出携带规则与包引用，新推导场景标为建议；接口适配缺少确认映射时应阻塞。执行凭据从运行环境获取，不写进上下文包。

依据：实施计划第 7 节。关联任务：P2-08、P3-02～05。状态：计划方案，适配器尚未实现。

### DEC-08：以独立评测和完整人工成本决定是否扩展

计划采用 3 个开发历史需求、2 个留出历史需求及 2 个真实新需求。留出答案独立受控保存，不进入 Agent 输入、事实库或 Skills；两个留出样本各运行 3 次。人工判定草稿准确性与召回率，初次草稿和确认后结果分别报告。

质量与收益阈值目前是建议目标，D2 在看结果前冻结。人工净节省包括材料、确认、修订、失败处理和维护成本；开发投入单列。只有历史回放时只能形成技术验收结论，不能替代真实需求收益验证或外推全团队收益。

依据：实施计划第 6、8、11 节、`evals/README.md`。关联任务：P1-05、P3-06、P4-01、04、05、07。状态：计划方案，尚无基准、业务评测或收益结果。

### DEC-09：工程框架保持最小可运行，实际数据与方法分离

项目根目录对应计划中的 `business-context/`；六个 Python 包各负其责。CLI 首先提供运行目录初始化，显式 `--data-dir` 优先于 `BUSINESS_CONTEXT_DATA_DIR`，默认 `.data/`；重复执行保留已有内容，路径冲突显式失败。

运行数据、凭据和数据库由忽略规则隔离，真实材料放独立受控目录；`.env.example` 只是说明，不自动加载。项目 Skills 保存方法与示例，业务事实留在事实库。当前四项 Skills 只有 README，占位目录不等于可加载能力。

依据：`README.zh-CN.md`、`src/workflow/`、`.gitignore`、`skills/README.md`。关联任务：P0-01～06、P1-07、13。状态：框架已落地，业务依赖及 Skills 待接入验证。
